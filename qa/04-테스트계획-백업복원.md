# 테스트 계획 — 백업/복원

| 항목 | 내용 |
|---|---|
| 대상 | 우리 가족 덴탈 관리 앱, 설정 화면의 "백업 만들기"·"백업에서 복원" |
| 대상 버전 | `main` 브랜치 (2026-11-25 기준) |
| 작성일 | 2026-11-25 |
| 기준 문서 | `README.md` 주요 기능("전체 기록을 백업 코드로 복사·붙여넣기"), 화면 문구 |

## 1. 목적

백업 코드로 **기록을 잃지 않고 그대로 되살릴 수 있는지**, 그리고 잘못된 코드를 넣었을 때 **기존 기록이 망가지지 않는지** 확인한다. 복원은 기존 기록을 모두 지우고 바꾸는 동작이라, 실패했을 때의 피해가 앱에서 가장 크다.

## 2. 범위

| 포함 | 근거 |
|---|---|
| 7개 표(구성원, 예방치료, 검진, 치아 상태, 치아 이력, 치과, 양치)의 왕복 보존 | 하나라도 빠지면 기록 손실 |
| 잘못된 코드 거부와 기존 기록 보존 | 화면이 "기존 기록은 그대로예요"라고 약속한다 |
| 교체 동작 (기존 기록이 있는 상태에서 복원) | 중복·잔여 데이터 위험 |
| 옛 형식 백업 (나중에 추가된 표가 없는 코드) | 오래 보관한 백업을 쓰는 것이 이 기능의 목적 |

| 제외 | 이유 |
|---|---|
| 클립보드·메신저를 거친 실제 전달 | 실기기와 메신저 앱이 필요하다. 수동 케이스로 남긴다 |
| 설정값(알림 시각, 테마) | 백업 대상이 아니다. 대상이어야 하는지는 기획 확인 사항으로 적는다 |
| 다른 시간대 기기에서 복원 | 테스트 환경의 시간대를 바꿀 수 없다. 리스크로 적는다 |

## 3. 접근 방법

| 수준 | 방법 | 대상 케이스 |
|---|---|---|
| 로직 | `flutter test qa/backup_cases_test.dart` 로 자동 실행 | F~H 그룹 29건 |
| 화면 | 앱을 실행해 손으로 확인 | N 그룹 9건 |

사용한 설계 기법: 동등 분할(정상 코드 / 형식 오류 / 구조 오류 / 값 오류), 경계값 분석(형식 버전 0·1·2, 한 글자 잘림), 상태 전이(빈 앱 ↔ 기록 있는 앱 ↔ 복원 실패), 오류 추정(메신저의 따옴표 변환, 손으로 고친 코드).

잘못된 코드 케이스는 모두 같은 방법으로 판정한다: **복원이 실패해야 하고, 실패 전후의 전체 기록이 같아야 한다.**

## 4. 환경

| 구분 | 내용 |
|---|---|
| 로직 테스트 | macOS, Flutter 3.44.1, 메모리 SQLite |
| 화면 테스트 | iOS 시뮬레이터 또는 `flutter run -d chrome` |
| 테스트 데이터 | 구성원 1명에 모든 종류의 기록을 1건 이상 넣은 상태를 기본으로 한다 |

## 5. 시작·종료 기준

- 시작: 앱이 빌드되고 기존 단위 테스트(`test/backup_service_test.dart` 포함)가 통과한다.
- 종료: 모든 케이스를 한 번씩 실행했고, 실패한 케이스마다 버그 리포트가 있다.

## 6. 리스크

| 리스크 | 대응 |
|---|---|
| 백업 코드가 길다. 양치 기록 3년 치(2명)에서 약 24만 자였다 | 메신저·메모장이 긴 글을 자르는지 수동 케이스(TC-N06)로 확인한다 |
| 날짜를 시각(밀리초)으로 저장한다. 시간대가 다른 기기에서 복원하면 생년월일이 하루 밀릴 수 있다 | 이번에는 확인하지 못했다. 시간대를 바꾼 기기에서 따로 확인해야 한다 |
| 복원 뒤 알림 재예약이 실패하면 화면은 "기존 기록은 그대로예요"라고 하지만 기록은 이미 바뀌어 있다 | 코드를 읽어 찾은 가능성이다. 재현하지 않았으므로 버그 리포트의 관찰 사항으로만 적는다 |
